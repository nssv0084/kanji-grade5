# このプロジェクトのレビュー

変更の差分を読み、下のチェックリストに沿って確認する。結果は日本語で、PR の説明に貼れる形にまとめる。

## 手順

1. 差分を取る。引数が PR 番号なら `gh pr diff <番号>`、なければ `git diff main...HEAD`。変更ファイルの一覧も見る。
2. `npm run verify` を実行し、結果を記録する（落ちていたらそれが最優先の指摘）。
3. 変更したファイルの種類に応じて、下の該当する観点だけを確認する。該当しない観点は「対象外」と書く。
4. 汎用のバグ検出が必要なら `/code-review` も実行し、結果を合わせる。
5. 指摘を重大度で並べる。

## 観点

### 要件とテスト（すべての変更）
- 機能の追加・変更なら、docs/requirements.md に番号つきの要件があるか。新しい番号は続き番号で、既存の番号を使い回していないか。
- 振る舞いを変えたなら、テスト名の先頭に対応する要件番号があるか。`npm run trace` で存在しない番号の参照がないか。
- 画面・データ・API の変更なら、docs/screens.md、docs/data-model.md も同じ変更で更新されているか。
- バグ修正なら、再発を防ぐテストがあるか。

### 認可と個人情報（backend/src）
- 新しい経路は backend/src/routes.ts の ROUTE_KEYS にあるか。保護者専用の機能は `/admin/` 配下か。
- 子どもが保護者の機能（問題の編集、写真、設定、アカウント）を呼べる経路がないか。sub を呼び出し元のトークンから取っているか。
- ログインID・ニックネームをログ出力していないか。学校名・メールアドレスを保存していないか（ACC-03）。写真の読み取り結果に名前を残していないか。エラー応答に内部の情報を出していないか。
- 正解を、解答前の応答に含めていないか。

### 写真と手書きの画像（S3、署名付き URL）
- バケットが非公開のままか。署名付き URL の有効期限が短いか（5分）。アップロードできる種類と大きさを制限しているか。
- ライフサイクル（写真30日、申し立ての画像90日）が保たれているか。
- 写真の文章をそのまま問題として保存していないか（GEN-01）。

### インフラ（infra）
- データを持つリソース（DynamoDB、Cognito）に削除保護（Retain）があるか。置き換えが起きる変更がないか。
- リソース名・スタック名が `Kanji` / `kanji` で始まり、同じアカウントの英検アプリのリソースと衝突・干渉しないか。OIDC プロバイダーを新しく作っていないか。
- IAM の権限が広がっていないか。ワイルドカード（`*`）を新たに許可していないか。広がる変更（経路の追加による Lambda の呼び出し許可なども含む）は、PR の説明に必ず書かれているか。GitHub Actions のデプロイは権限の確認を出さない（`--require-approval never`）ため、ここと production 環境の承認が確認の場になる。
- 公開範囲が広がっていないか（S3 の公開、CORS の許可元）。
- AWS のアカウント固定（infra/config.ts の accountId、check-account）を迂回していないか。

### AI 利用（読み取り・生成・検証・手書き判定）
- プロンプトの変更なら、試した結果（読み取りの正確さ、承認率、問題の例）が PR に書かれているか。書かれていなければ「要確認」にする。
- 費用の記録と、予算の90%で止まる仕組みが保たれているか。手書きの判定に AI を使っていないか（HWR、4.1）。
- 生成した内容を、機械的な検査（配当表・読み）と検証を通さずに出題対象にしていないか。
- モデル名を、設定画面の値ではなくコードに固定していないか。

### 手書き判定（frontend の手書き、shared の照合）
- しきい値を変えたなら、その根拠（サンプルや申し立ての記録での誤判定率）が PR に書かれているか。
- 書いている間にページがスクロール・拡大しないか。1画もどす・書き直すが動くか。
- KanjiVG のデータを加工したなら、クレジットとライセンス（CC BY-SA 3.0）の表記が保たれているか。

### 学習ロジック（shared、backend/src/lib/study）
- 日付の区切り（日本時間の午前3時）を `studyDate` 以外で計算していないか。
- 習っていない漢字が答えに入る問題を出していないか（CUR-01、CUR-05）。

### 画面（frontend）
- スマホ幅（390px、小さい端末は 360px）で崩れていないか。PC 幅でも使えるか。操作できる要素が小さすぎないか（目安 44px 以上）。
- 小学5年生が読める言葉・漢字で書かれているか（5年生で習っていない漢字にはふりがなを付けるか、ひらがなにする）。
- エラー時の表示と、読み込み中の表示があるか。

### リポジトリ全体
- API キー、アクセスキー、パスワード、子どもの個人情報・筆跡のサンプルが差分に含まれていないか。
- .github/workflows、.claude/hooks、.claude/settings.json の変更は、止める線を弱めていないか。弱める変更は必ず「重大」にして、理由の説明を求める。
- 依存パッケージの追加は、必要性とライセンスを確認する。

## 出力の形式

```
## レビュー結果
- verify: 成功 / 失敗（内容）
- 対象にした観点: （例）要件とテスト、認可、インフラ

### 重大（マージ前に直す）
- ファイル:行 — 指摘と理由

### 要確認（判断が要る）
- ファイル:行 — 指摘と理由

### 提案（任意）
- ファイル:行 — 指摘

### 問題なし
- 確認して問題なかった点を1〜3行
```

指摘がなければ、各見出しを「なし」とする。推測で指摘せず、根拠のあるファイルと行を示す。
